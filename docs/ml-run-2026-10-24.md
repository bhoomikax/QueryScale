# Measured ML run, 2026-10-24

Record of the first training run after the ML pipeline was made persistent (durable sample
store, atomic model publication, feature-schema validation, eligibility status). Every number
below is copied from a generated file on the machine that ran it; those files
(`data/benchmark_history.jsonl`, `data/ml_dataset.sqlite3`, `models/*.json`) are gitignored and
change on every run, so this file is the durable record. Nothing here is a claim about general
index quality: one workload, one dataset, one laptop, no concurrent load.

## Follow-up the same day: one benchmark protocol

The first pass left three workload signatures in the store: 24 label-pass runs (200
iterations, 2 repeats), the pipeline's own benchmark (200 × 1) and an API run (50 × 2). The
two odd runs were correctly excluded as `different_workload`, but eligibility counted all 26
valid rows while training used 24. Both were fixed: `BENCHMARK_ITERATIONS` / `BENCHMARK_REPEATS`
now define one label protocol that the dashboard, API, `collect_benchmark_labels.py`,
`run_local_pipeline.py` and the benchmark CLI all default to, every run records whether it
matches that protocol, `GET /api/benchmark/protocol` shows the effective settings, and
eligibility counts only the dominant signature. The two odd runs stay in the history and the
store as excluded samples; nothing measured was deleted.

During this follow-up a new test fixture briefly wrote six mocked benchmark records (mocked
dataset signature `D`, no measured index size) into the real history while the suite ran next to
the API. They were removed again by that unambiguous marker (backups in `data_backup/`), the
fixture now redirects history, results and store paths to a temporary directory, and a suite run
was shown to leave the history line count unchanged.

Final state after two more label-protocol runs of the top candidate (one from the API, one from
the CLI): 28 valid measured runs, 26 comparable across 12 candidates, model
`v20261024T201227Z-7d6936618995`, selected `decision_tree` by grouped CV MAE (0.0796 vs ridge
0.1027, random forest 0.1012, gradient boosting 0.1013, baseline 0.1427); held-out MAE 0.0686
beats the baseline 0.0776, so it is active. Random forest again had the lowest held-out MAE
(0.0612). On the 3 held-out candidates the tree's ranking equalled the rule score's (NDCG@5 0.928,
Precision@5 0.6, Spearman 0.478). Leave-one-out per-candidate MAE: baseline 0.105, ridge 0.074,
decision tree 0.050, random forest 0.045, gradient boosting 0.030. The selected model changed
from ridge to a decision tree by adding two runs of one candidate, which shows how unstable
selection is at this sample size.

## Limitations

1. 12 candidates, 3 held out: the training-report ranking metrics are computed over
   effectively three items.
2. One workload, one dataset, one machine. Transfer to other schemas is untested.
3. Two Transactions candidates dominate the error improvement.
4. Reranked recommendations are in-sample; agreement with labels there is expected.
5. Write-probe overheads (25 single-row probes, rolled back) are noisy and not used as labels.
